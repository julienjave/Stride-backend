# The patient's loop: a session the database can vouch for

This entry covers the backend side of the frontend's Phase 4
(2026-10-15 → 2026-10-19): the patient starts a session, ticks exercises,
finishes it — or stops, or skips — and the practitioner reads what happened.
That record is clinical. A practitioner adjusts a treatment from it, and a
reviewer may ask months later what the patient reported and when. So before
any patient screen was built, the session itself was rebuilt to be
trustworthy, and most of that trust ended up in the database.

Condensed to four stories; the full list is in [`PROJECT.md`](../PROJECT.md).
The screens' side is the frontend journal's Phase 4 entry
(`docs/journal/02-the-patients-loop-on-a-phone.md`, TODO-LINK).

## A state machine whose states the database knows

Before this phase a session had five statuses (`pending` among them), a
`completedAt` the client chose, nothing saying why a session ended
unfinished, and exercises that could still be ticked on a finished one.
Migrations 0037 and 0038 replaced that with four statuses and fixed ways
between them: `in_progress` → `completed` (only on its own day),
`incomplete` (stopped by the patient with a reason, or closed by the app),
and `skipped` (never started). There is no `pending`. A row exists only once
the patient *acts*, and sessions not done yet are computed by the schedule
module (entry 36), never stored.

Three choices make the database the judge rather than the service:

- **One CHECK per rule.** Which moments each status carries, a reason
  exactly when stopped or skipped, a note only with a reason, check-out
  scores only on an ended session, a skip that records no work: each is its
  own named constraint, so a refusal says *which* rule it broke.
- **No default for `status`.** With a default, an `INSERT` that forgets the
  status silently writes one; without one, it fails. Removing it at once
  surfaced the test set-ups that had relied on the old default — exactly
  where they needed fixing.
- **A trigger for what a CHECK can't see.** A CHECK sees one row;
  "a finished session never changes" is about two versions of it. The
  `BEFORE UPDATE` trigger compares `OLD` and `NEW`. A finished session is
  final, its identity (program, workout, day) is fixed, and every moment it
  sets must equal `now()`. In Postgres `now()` is the *transaction's* start,
  so the service writes ``sql`now()` `` and anything else (a client's clock,
  a script's `new Date()`) is refused.

"At most one open session per program" and "one skip per day" are **partial
unique indexes** (`WHERE status = 'in_progress'`, `WHERE status =
'skipped'`). A service check of the form "is one open? if not, insert" has
two steps that two requests can both pass; the index makes the second
`INSERT` wait for the first transaction, then fail with `23505`, which
becomes a `409`. Migration 0037 was generated by drizzle-kit, then edited by
hand — the fifth migration to need it. A constraint checks every existing
row, so the rows it would refuse had to be repaired first, in the right
order, before the constraints were added.

## Races a plain read can't see

The checklist's guard (`guard_session_exercise_open`, 0038) refuses a tick
on a session that isn't open. The interesting part is *how* it reads the
session. A patient taps Finish in one tab and ticks an exercise in another.
Finish holds the session's row lock, not yet committed. A plain read inside
the tick's trigger sees its own snapshot (the session still open) and would
let a tick land on a session that is about to be final. Reading the session
`FOR SHARE` conflicts with Finish's `FOR UPDATE`, so the tick waits for the
commit, re-reads, and is refused.

The tests prove each race deterministically, with a helper that became a
project fixture, `whileHolding`. It runs a write on another connection
*without committing*, sends the request, checks the request is still waiting
after 300 ms, then commits and checks the answer. A request that waited
proves a lock or a constraint was involved, and the answer proves it decided
right. It was used for one open session, one skip a day, a tick racing a
Finish, and a Finish racing a program's closing.

That last race came from a rule reversed at the person's request. Closing a
program used to leave its open session open. That made no sense, but it
collided with a rule held since migration 0004: only the patient writes
their own sessions. Migration 0039 handled it in two parts, each doing what
it can:

- a new `UPDATE` policy lets the care team update a session row at all.
  Postgres policies are *permissive* by default (a row passes if any policy
  allows it), so it adds to the patient's own;
- the trigger then narrows that to exactly **one** change: `in_progress` →
  `incomplete`, reason `program_closed`, at `now()`, on a program that is
  closed, with every other column unchanged. "Every other column unchanged" is
  one comparison that survives columns added later:
  `to_jsonb(NEW) - 'status' - 'end_reason' - 'ended_at' = to_jsonb(OLD) - …`.

A policy says which *rows*, a trigger says which *values*: the pattern
reappears in entries 38 and 40. A `SECURITY DEFINER` function was weighed
and refused here. It would skip row security altogether, and the write would
no longer be the practitioner's own, under their own context. (Entry 40
shows the case where one *was* the right answer.)

The suites themselves needed a fix to keep testing this honestly. They send
far more requests than a person, and step 1b's tests hit the limit of 60 a
minute per route. Files had been split and fixtures shared just to stay
under it, while no test proved the limits worked at all. `RATE_LIMITS=off`
now switches them off for every e2e file. It is absent-means-on and refused
in production, and one suite, `test/rate-limits.e2e-spec.ts`, turns them
back on to prove the 6th sign-in and the 61st request are refused.

## A suggestion is not a rule

Late make-ups (a missed day made up after its window, opt-in per program)
were designed with the person before any code. Measuring the existing module
first, on the real code rather than by assumption, turned up a gap. A
session done early for a later day and an ordinary make-up on the same free
day *both* counted: two sessions credited to one day, no extra reported. Each
kind of session had its own list with its own rule, and nothing looked at
the day as a whole. The module now collects every **candidate** for a day,
each carrying what counting it would do (an `apply` closure), and `settle()`
applies only the first created. Migration 0041 added the database's half:
a start on a day that already has a completed session is refused, by a
trigger reading the siblings `FOR SHARE`. `FOR SHARE` needs the `UPDATE`
privilege *and* passes through the `UPDATE` policy, so a policy limited to
open sessions would silently filter completed ones out and the trigger
would never refuse. The policy was read from `pg_policy` before relying on
it.

Then came a correction worth more than the feature. The delivery said a late
make-up would wait "for another free day" while an on-time catch-up was
open. The person asked whether the coming Sessions hub would therefore
*refuse* the late one, and it would have: `catch_up_first` was a server
refusal. A screen's priority ("show the on-time one first") had been written
as a server rule, which binds every client forever. It was removed. The
server enforces what must hold, such as one session a day or a free day;
screens decide what to suggest.

## Time, and the network, done on purpose

Two bugs from this phase came from defaults nobody had chosen.

**Photo uploads that waited 6 seconds each.** The person reported that
uploading photos "takes forever". The AWS SDK adds `Expect: 100-continue` to
every request body over 2 MB, and Node then waits up to 6 seconds for a
"100 Continue" the storage server may never send. The storage client had no
timeouts either. `storageClientConfig()` now drops the header and sets
connection and request timeouts that *throw* (`throwOnRequestTimeout` —
without it an exceeded timeout is only a warning). It is tested on a real
local socket, since a mocked `send()` can't show a header on the wire. The
person's own photo, though, was 450 KB and could never trigger it. Narrowing
one layer per test on their machine — a probe script straight to storage
(44 ms), the same photo POSTed from Node (167 ms), Firefox and Edge (fine) —
showed their Chrome never sent the request at all. That one wasn't Stride's
bug; it stays recorded so nobody goes looking for it in the code.

**An invitation that lived 169 hours.** The invitations e2e test measured
608,400,000 ms instead of 604,800,000. The sandbox's Postgres ran on Paris
time in the week before the clocks went back, and
`now() + make_interval(days => 7)` is *calendar* arithmetic: on a
`timestamptz`, days and months are computed in the session's time zone
("the same wall-clock time, N dates later"). A lifetime is a duration, so
`invitationExpiry(from)` now adds 168 hours. Because it takes its start as
a parameter, a test can run it at a date next to a clock change, under
`SET LOCAL timezone = 'Europe/Paris'`, on every day of the year — not only
in the one week a year when the old test could fail.

The practitioner's "For review" list closed the phase with a design worth
noting. Alerts (missed sessions in a row, inactivity, a painful session) are
**computed per request**, in a fixed number of queries, and never stored. A
stored alert must be kept true by a job, and a job has no user to sign its
audit entries (`performed_by` is NOT NULL). Only the human act is stored:
a practitioner's review of a session (`session_reviews`, migrations
0043–0044, idempotent with `INSERT … ON CONFLICT DO NOTHING`). The question
of a job with no user came back in entry 40, and was answered there.
